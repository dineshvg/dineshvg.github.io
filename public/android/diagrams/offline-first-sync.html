Offline-first sync

Use it when: asked to design an app that works without a connection, such as viewing and redeeming prescriptions.

sequenceDiagram
  participant UI as UI
  participant R as Repository
  participant DB as Local database: source of truth
  participant API as Remote API
  UI->>R: user action
  R->>DB: write change, mark pending
  DB-->>UI: Flow emits updated data
  Note over UI,DB: the UI always observes the database, never the network
  R->>API: sync pending change when online
  alt accepted
    API-->>R: ok
    R->>DB: clear pending mark
  else conflict
    API-->>R: conflict
    R->>DB: apply the conflict rule, flag for the user if needed
  else offline or error
    R->>R: keep pending, retry with backoff
  end
  DB-->>UI: Flow emits final state

Say it like this

  1. The local database is the single source of truth; the UI observes it and never waits on the network.
  2. Writes land locally first with a pending mark, so the app works offline.
  3. A sync step pushes pending changes; decide the conflict rule up front (server wins, last write wins, or ask the user) and say why.
  4. Retries need backoff and idempotent requests.
  5. For health data, also cover encryption at rest, consent and expiry, and what happens when a prescription changes server-side while offline.

Source

  • Persisting data for offline use, single source of truth and UI driven from data models: reading list R9.
  • The sync protocol and conflict handling are design choices, not from the sources.

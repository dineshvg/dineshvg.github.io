Testing pyramid with agent-era gates

Use it when: asked about test strategy, or how you trust agent-written tests.

flowchart TD
  E2E["End-to-end and UI flows on a device<br/>few, slow, high confidence per test"]
  INT["Integration tests across modules<br/>some, medium speed"]
  UNIT["Local unit tests on the host<br/>many, fast, run on every change"]
  JNY["Journeys: LLM-driven checks of critical flows<br/>extra gate, less deterministic"]
  MUT["Check the tests: break the code on purpose,<br/>review assertions, prefer fakes over mocks"]

  UNIT --> INT --> E2E
  JNY -.-> E2E
  MUT -.-> UNIT

  classDef few fill:#fecaca,stroke:#b91c1c,color:#1c1917
  classDef some fill:#fde68a,stroke:#b45309,color:#1c1917
  classDef many fill:#bbf7d0,stroke:#15803d,color:#1c1917
  classDef extra fill:#c7d2fe,stroke:#4338ca,color:#1c1917
  class E2E few
  class INT some
  class UNIT many
  class JNY,MUT extra

Say it like this

  1. Base: many fast local unit tests. Middle: fewer integration tests. Top: a small number of slow device flows.
  2. Journeys add another check of critical flows but are LLM-driven, so keep deterministic tests as the CI gates.
  3. With agents writing tests, the risk is tests that pass while proving nothing: break the production code on purpose and see them fail.
  4. Prefer fakes (working in-memory implementations) over mocks that merely verify calls.

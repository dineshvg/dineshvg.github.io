Compose phases and deferred reads

Use it when: asked why something recomposes, or how to reduce recomposition work.

flowchart LR
  ST["State changes"] --> COMP["Composition<br/>what to show"]
  COMP --> LAY["Layout<br/>measure and place"]
  LAY --> DRAW["Drawing<br/>render pixels"]

  RC["Read state in the composable body"] -.->|"invalidates"| COMP
  RL["Read state in a layout lambda<br/>for example Modifier.offset"] -.->|"invalidates"| LAY
  RD["Read state in a draw lambda"] -.->|"invalidates"| DRAW

  classDef phase fill:#c7d2fe,stroke:#4338ca,color:#1c1917
  classDef read fill:#fde68a,stroke:#b45309,color:#1c1917
  classDef start fill:#bae6fd,stroke:#0369a1,color:#1c1917
  class COMP,LAY,DRAW phase
  class RC,RL,RD read
  class ST start

Say it like this

  1. A frame has three phases: composition, layout, drawing.
  2. Where you read state decides which phase it invalidates; reading in the composable body re-runs composition, reading inside a lambda modifier defers the read to a later phase.
  3. So "defer state reads with lambdas" means cheaper updates, as in Modifier.offset { ... }.
  4. Confirm with recomposition tracing (Compose 1.13) instead of guessing.

Source

  • The three phases and the "defer reads" best practice: reading list R14; recomposition tracing: R1. Which phase each read invalidates is standard Compose behavior, stated here from general knowledge.

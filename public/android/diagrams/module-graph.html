Module graph

Use it when: asked how you would split an app into modules and keep teams from coupling.

flowchart TD
  app[":app: wiring only"]
  subgraph FEATURES["Feature modules"]
    f1[":feature:prescriptions"]
    f2[":feature:profile"]
    f3[":feature:settings"]
  end
  subgraph CORE["Core modules"]
    cui[":core:ui"]
    cdata[":core:data"]
    cnet[":core:network"]
    cmodel[":core:model"]
  end
  app --> f1
  app --> f2
  app --> f3
  f1 --> cui
  f2 --> cui
  f3 --> cui
  f1 --> cdata
  f2 --> cdata
  cdata --> cnet
  cdata --> cmodel
  cui --> cmodel
  f1 -.-x f2

  classDef app fill:#fde68a,stroke:#b45309,color:#1c1917
  classDef feature fill:#c7d2fe,stroke:#4338ca,color:#1c1917
  classDef core fill:#bbf7d0,stroke:#15803d,color:#1c1917
  class app app
  class f1,f2,f3 feature
  class cui,cdata,cnet,cmodel core

The crossed dotted line between two feature modules marks the rule: features never depend on each other.

Say it like this

  1. The app module only wires features together; features never depend on each other.
  2. Shared code lives in core modules with a clear purpose; dependencies point toward stable, low-level modules.
  3. Mark everything except the public interface internal so the compiler enforces boundaries.
  4. Watch granularity: too fine means overhead, too coarse means a new monolith.
  5. Enforce the rules automatically with dependency graph checks in CI.

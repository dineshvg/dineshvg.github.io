02 · Architecture and modularization

Priority P15htodoverified 2026-11-16

Practice 14 flashcards

For an architect role this is the core: layers, boundaries, and the trade-offs behind them.

Why it comes up

  • Whiteboard rounds ask you to structure an app and defend module boundaries.
  • Follow-ups probe trade-offs: granularity, dependency direction, DI, migration path.

Know cold

From R9 and R10 unless marked.

  • Principles: separation of concerns; drive UI from (preferably persistent) data models; single source of truth (one owner exposes data immutably and handles changes); unidirectional data flow (state flows down, events flow up).
  • Layers: UI layer (Compose plus state holders such as ViewModel), data layer (repositories and single-source data sources), optional domain layer of single-purpose use cases, added only when logic is complex or reused.
  • Dependency management: the guide recommends dependency injection and names Hilt. Koin appears as a migration target in the Android Bench tasks (R5), so know both and the criteria (compile-time validation vs simplicity, multiplatform needs).
  • Modularization: organizing code into loosely coupled, self-contained parts with a clear purpose. Benefits: reusability, strict visibility (internal or private for everything except the public interface), customizable delivery, plus scalability, ownership, testability and build time.
  • Pitfalls: modules too fine-grained (overhead) or too coarse (a new monolith); not worth it for projects that will not grow.
  • Common practice, not from the sources: split public API from implementation for shared modules, forbid feature-to-feature dependencies, share Gradle configuration through convention plugins, and check the dependency graph in CI.
  • Architect framing (iSAQB style): name the quality goals, record decisions as ADRs (context, options, consequences), and state what you gave up.

Likely questions

Question What a strong answer contains
When do you add a domain layer? Only for reused or complex logic; otherwise it is ceremony. Give an example of each.
How do you decide module boundaries? By cohesion and change frequency, ownership, build time and visibility needs; start coarse, split with evidence.
What goes wrong with too many modules? Build and configuration overhead, boilerplate, hard-to-find code; cite R10's pitfalls and a number from your own experience.
How do you stop features coupling to each other? Dependency rules, shared contracts in a core module, graph checks in CI.
Single source of truth in an offline-first app? Local database as the SSOT, network as a data source that refreshes it, UI observing the database.
Hilt or Koin? Criteria and a decision, not a preference; mention testing and multiplatform.
You inherit a monolith. How do you modularize without stopping features? Incremental extraction by seams, strangler approach, measure build time as you go, ADR per step.

  • ☐ Write one ADR for a module-boundary decision.
  • ☐ List three modularization pitfalls you actually hit and how you fixed them (story 1 or 3 in the story bank).

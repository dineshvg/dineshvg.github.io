05 · Testing and verification

status: todo · priority P1 · 4h · verified 2026-11-16

Practice 9 flashcards

Agent-written code makes test quality the main safeguard, so interviewers probe what your tests actually prove.

Why it comes up

  • A recent thread claims an agent can reveal that mock-based tests verify nothing (anecdotal, see notes).
  • Leads own the test strategy, not just individual tests.

Know cold

From R15 and R11 unless marked.

  • What the official docs cover: fundamentals, local unit tests on the host, instrumented tests on devices or emulators, behavior and screenshot tests for UI, testing different screen sizes, and tools such as Robolectric, Espresso and UI Automator. The "test doubles" and "testing strategies" pages sit under the index; open them for the official wording.
  • General background, not from R15: a fake is a lightweight working implementation (an in-memory repository); a mock records and verifies interactions; the testing pyramid has many fast unit tests, fewer integration tests, few slow end-to-end tests.
  • Coroutine tests: inject dispatchers and use runTest with a test dispatcher (R11).
  • Journeys (R2): natural-language user-journey checks that agents run; useful as an extra gate, not a replacement for deterministic tests (my reasoning).
  • Verifying agents: gates in order of cost: compile and lint, unit tests, integration tests, device journeys, human review. A green suite proves only what the tests assert.

Likely questions

Question What a strong answer contains
Fakes or mocks, and why? Fakes for state and behavior, mocks for verifying interactions at boundaries; mock-heavy tests assert implementation, not behavior.
How do you know your tests are good? Mutation testing or deliberately breaking code, failure messages that point to causes, tests that survive refactors.
What is your strategy for a multi-module app? Fast module-local tests, a few cross-module integration tests, a small set of end-to-end flows.
How do you handle flaky UI tests? Quarantine, find the cause (timing, shared state, animations), fix or delete; never ignore in CI.
An agent wrote 40 tests that pass. Do you trust them? Review assertions, break the code and see them fail, check they test behavior.
What do you test on a real device vs an emulator? Hardware, OEM behavior and performance on devices; logic and UI flows on emulators.

Practice

  • ☐ Take one existing mock-heavy test and rewrite it with a fake; note what the new test catches that the old one missed.
  • ☐ Break production code on purpose and check which of your tests fail.
  • ☐ Add story 2 to the story bank.

01 · Agentic Android development

status: todo · priority P1 · 6h · verified 2026-11-16

Interviewers increasingly ask how you use coding agents and, more importantly, how you know their output is right.

Why it comes up

  • Android Dev Summit 2026 centred on agents, and a recent r/androiddev thread claims candidates are expected to know the tooling (anecdotal, see notes).
  • Architect and lead roles are asked about policy: what you delegate, what you review, what you forbid.

Android CLI (R1, R2)

Command Purpose

android docs search Search the Android Knowledge Base
android skills list / add Browse and install skills
android preview Render Compose Previews without an emulator or IDE
android device remote Use a real device from a Google device lab
android profiler System traces via Android Performance Analyzer

android analyze R8 shrink and obfuscation report, JSON for CI
android studio ... Let any agent use Studio's analysis (needs the Quail preview and an open project, per R2)

Journeys (R2): natural-language descriptions of core user experiences, saved in the project, which any agent can run through the CLI by navigating the app as a user.

Skills (R4): SKILL.md files with task specifications; 30+ across 20+ areas, evaluated, aimed at areas where models often fall short. Install with android skills add <name>.

Claude Code plugin (R3): /plugin marketplace add android/android-cli-plugin, then /plugin install android-cli@android-cli-plugin.

ACP (R8): standardizes communication between editors and coding agents (local over stdio, remote over HTTP or WebSocket) and reuses MCP's JSON representations where possible. The recap R6 frames it as ACP for building in the IDE, MCP for agents using tools or your app; treat that framing as the author's.

Android Bench (R5): 30 tasks, 5 runs each, covering app conversion, creation, migration and new features on real open-source apps; reports pass rate, completion rate, latency and cost. When fetched, the best visible pass rate was about 40%. Lesson: even top model-agent pairs fail most multi-day tasks without supervision.

Vendor claims, not independent results (R1): android preview made UI tasks 77% faster with up to 3x fewer tokens; the LeakCanary tool made top models about 2x faster with up to 25% fewer tokens (tested with Claude Opus 5.5).

Process pattern worth borrowing (R7): one task per agent session, one PR per task, a written plan approved before coding, and review checkpoints for spec, plan and code.

Likely questions

Question What a strong answer contains
How do you use agents day to day, and what do you not delegate? A concrete workflow (spec, plan, implement, verify), plus explicit no-go areas such as crypto, auth and architecture decisions.
How do you verify agent output? Layered gates: build, deterministic tests, Journeys on a device, previews or screenshots, profiler for performance, then human review. Mention test quality, not just coverage.
ACP vs MCP? ACP connects editor and agent; MCP connects agent and tools. They share JSON representations.
Would you allow agents in a regulated health codebase? Controls: approved models, no secrets or patient data in prompts, scoped repo access, PR-only changes with review, audit trail, license check. Your own policy, not a slogan.
Is prompting a durable differentiator? Tool-specific prompting decays quickly; durable skills are decomposition, specs, building verification harnesses and judging diffs.
What do Android Bench results tell you? Agents help but are not autonomous on long tasks; pass rates are far from 100%, so verification is the job.
Where do Journeys fit next to Espresso or UI Automator? My reasoning, to test yourself: Journeys are LLM-driven and so less deterministic, which suits exploratory and critical-path validation; keep deterministic tests as CI gates.

Practice

  • ☐ Install the CLI (android init) and the Claude Code plugin on a real module. Write down what the agent did well and where it needed correction.
  • ☐ Write three Journeys for one critical flow, run each five times, and log pass or flake.
  • ☐ Compare your Conduit MCP server with CLI plus Journeys on device control, UI inspection, test authoring, CI use, determinism and extensibility.
  • ☐ Write a one-page agent policy for a regulated codebase.
  • ☐ Add story 2 (an agent was wrong and you caught it) to the story bank.

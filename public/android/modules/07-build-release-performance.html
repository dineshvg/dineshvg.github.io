07 · Build, release and performance

status: todo · priority P2 · 4h · verified 2026-11-16

Leads own delivery: build speed, app size, startup, and safe releases.

Why it comes up

  • Questions about CI pipelines, release trains and "why is our build slow" test operational judgment.

Know cold

From R17 and R1 unless marked.

  • Baseline Profiles: let ART compile specified code paths ahead of time (startup, navigation, scrolling), avoiding interpretation and JIT on first launch; the page cites about a 30% speed improvement. Rules ship as assets/dexopt/baseline.prof. Startup Profiles are complementary: R8 uses them to reorder DEX code.
  • Generate vs release: generate profiles from a non-obfuscated, non-optimized benchmark variant; ship an obfuscated, optimized release build (R8 rewrites the rules). Tooling: Baseline Profile Gradle plugin with AGP 8.0+, Macrobenchmark 1.5.0+, profileinstaller 1.4.1+.
  • Limits: Cloud Profiles need Android 9+; some non-Play channels and Play internal app sharing do not support profiles at install; some OEM battery optimizations interfere.
  • R8 and size (R1): the R8 Configuration Analyzer in AGP 9.3 scores your configuration and ranks keep rules by cost (./gradlew :app:analyzeReleaseR8Config); android analyze reports shrink and obfuscation quality with JSON output for CI; Jetpack Keep (alpha) replaces broad keep rules with annotations.
  • Tracing (R1): androidx.tracing 2.0 adds source location and connected coroutine flows; Compose 1.13 adds recomposition tracing.
  • Lightbuild (R1): early preview, declarative YAML build; Google says keep using Gradle and AGP for production.
  • Production signals (R1): Crashlytics heap dumps from OOMs (early access); android signals lists crashes, ANRs and memory issues.
  • Your own pipeline experience: Fastlane, Jenkins and Play Store release practice come from your work; no verified source was gathered yet.

Likely questions

Question What a strong answer contains
How would you cut cold-start time? Measure first (Macrobenchmark), then Baseline Profiles, lazy init, fewer startup providers; verify with before and after numbers.
How do you keep release size in check? R8 shrinking, keep-rule review, size gates in CI via android analyze.
Describe your release pipeline. Trunk or release branches, signing, staged rollout, monitoring, rollback criteria.
Build is slow in a 40-module project. What do you check? Build scans, module graph shape, caching, annotation processing cost; general practice, so back with your numbers.
How do you decide when a release is safe? Gates (tests, size, profile checks), crash-free rate thresholds, staged rollout stop conditions.

Practice

  • ☐ Generate a Baseline Profile for one flow and measure cold start before and after.
  • ☐ Run android analyze (or the R8 analyzer task) on a release build and list the three costliest keep rules.
  • ☐ Write your release pipeline as a diagram.

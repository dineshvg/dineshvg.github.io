04 · Compose state and performance

Priority P24htodoverified 2026-11-16

Practice 12 flashcards

Expect a deep dive on where state lives and why something recomposes.

Why it comes up

  • Compose is the default UI toolkit; leads are asked to review and design state handling, not only write it.

Know cold

From R13 and R14.

  • State and composition: Compose is declarative; recomposition happens when state changes, and composables update only when they receive new arguments.
  • remember and mutableStateOf: remember keeps an object across recompositions; mutableStateOf creates observable state. rememberSaveable survives configuration changes but not the user dismissing the activity; non-Bundle types need a saver.
  • Stateful vs stateless; hoisting: replace internal state with a value parameter and an onValueChange event so the caller owns state. This gives a single source of truth and unidirectional data flow. Plain state-holder classes can own logic and state.
  • Other state sources: Flow via collectAsStateWithLifecycle(), LiveData, RxJava, and produceState for custom sources.
  • Performance model: three phases (composition, layout, drawing); stability; Baseline Profiles; release builds with R8.
  • Best practices (R14): remember for expensive work; stable key and contentType in lazy layouts; derivedStateOf (or computedStateOf in Compose 1.13+) for fast-changing state; defer state reads with lambdas and lambda modifiers such as Modifier.offset { }; avoid backwards writes.
  • Tooling: Compose 1.13 recomposition tracing shows which functions recomposed and the state write that caused it (R1).
  • Vendor claim: Google's benchmarks report Compose matching Views for scroll jank since Compose 1.9.0 (R14).

Likely questions

Question What a strong answer contains
Where should state live? Hoist to the lowest common owner; business state in a ViewModel, UI-only state in a state holder or remember.
Why does this composable recompose too often? Unstable parameters, reading state too early, lambdas capturing changing values; how to confirm with recomposition tracing.
remember vs rememberSaveable? Survival across configuration changes and process death, and the cost of saving.
derivedStateOf: when and why? Converts rapidly changing input into rarely changing output to limit recomposition.
How do you make a long list scroll smoothly? Keys and content types, avoid heavy work in composition, Baseline Profiles, release build.
How do you test Compose UI? Behavior tests on semantics, screenshot tests, previews as a fast check (see module 05).

Practice

  • ☐ Take a screen with an unstable parameter, find the extra recompositions with the profiler, fix, and record before and after.
  • ☐ Hoist state out of a stateful composable and explain the testability gain aloud.

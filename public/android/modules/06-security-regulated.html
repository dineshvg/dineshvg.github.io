06 · Security for regulated apps

status: todo · priority P2 · 4h · verified 2026-11-16

In health and public-sector apps, security is part of architecture; expect scenario questions, not trivia.

Why it comes up

  • Regulated employers test whether you design for threats, data minimization and auditability.
  • With agents in the workflow, "who reviews generated code for security" is a new follow-up.

Know cold

From the security checklist, R16 (page last updated 2026-09-01) unless marked.

  • Checklist areas: authentication, app integrity, data storage, permissions, networking, input validation, user data, WebView, credential requests, API key management, cryptography, interprocess communication, dynamically loaded code, virtual machine and native code.
  • Concrete rules from the page: keep content providers private (android:exported="false") unless needed; use parameterized queries, not concatenated input; prefer explicit intents, since binding a service with an implicit intent throws on API 21+; initialize keys with SecureRandom; use 256-bit AES for commercial purposes (128-bit if unavailable).
  • Agent-related security skills (R1): android-intent-security and android-permissions-security give project-aware reviews with fixes; play-policy-insights audits against Play policy and is advisory, not legal advice.
  • Your own domain experience: certificate transparency, app-to-app communication and push notification security are areas you work in. Prepare real examples.

Likely questions

Question What a strong answer contains
Walk me through the threat model of an app handling prescriptions or health data. Assets, attackers, trust boundaries, data at rest and in transit, what you log, what you never log.
How do you secure app-to-app communication? Explicit intents, permission checks, caller verification, minimal exported surface.
Where do keys and tokens live? Hardware-backed keystore where available, short-lived tokens, no secrets in the repo or APK.
How do you protect against a compromised network? TLS, pinning or transparency checks and their operational cost (rotation, outage risk).
How do you review agent-generated code for security? Same bar as human code plus targeted skills, secret scanning, dependency and permission diffs, no data in prompts.
What do you log and what do you refuse to log? Minimal, no personal or health data, correlation IDs instead.

Practice

  • ☐ Write a one-page threat model for an app you know (assets, actors, boundaries, mitigations).
  • ☐ Audit one manifest for exported components and over-broad permissions; note fixes.
  • ☐ Add story 6 (a security or compliance trade-off) to the story bank.
